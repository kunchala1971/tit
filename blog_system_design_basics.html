System Architecture

System Design Fundamentals for Developers

Learn the foundational concepts required to architect high-throughput, fault-tolerant distributed web applications: scaling models, load balancing, caching, database sharding, and CAP theorem.

By KSR 15 min read Updated September 2026

When scaling applications from hundreds of users to millions of concurrent requests, monolithic single-server architectures fail. System design is the art of organizing software components, databases, load balancers, and caches to achieve high availability, fault tolerance, and low latency.

1. Vertical vs Horizontal Scaling

Scalability measures an application's ability to handle growing workload seamlessly.

Vertical Scaling (Scale Up)

Adding more CPU cores, RAM, or SSD storage to an existing single server instance.

  • Pros: Simple setup, no code changes required.
  • Cons: Hard hardware limits, single point of failure (SPOF), expensive server costs.
Horizontal Scaling (Scale Out)

Adding more server instances behind a load balancer to distribute request traffic.

  • Pros: Unlimited scalability, high fault tolerance, cost-effective commodity servers.
  • Cons: Requires stateless app design & complex load balancing.

2. Load Balancers & Traffic Algorithms

A Load Balancer sits between client browsers and backend app servers, distributing incoming traffic across healthy instances.

Algorithm How It Works Best Use Case
Round Robin Distributes requests sequentially to each server in order. Homogeneous server clusters with equal capacity.
Least Connections Routes traffic to the server with the fewest active connections. Long-lived HTTP requests or WebSocket connections.
IP Hash Hashes the client's IP address to map them to a specific server. Sticky sessions requiring stateful user persistence.

3. Caching Strategies (Redis / Memcached)

Caching stores frequently requested data in high-speed RAM to eliminate redundant database queries.

// Cache-Aside Pattern Implementation
async function getUserProfile(userId) {
  // 1. Check Redis cache first
  const cachedUser = await redis.get(`user:${userId}`);
  if (cachedUser) return JSON.parse(cachedUser);

  // 2. Cache miss: fetch from SQL database
  const user = await db.query('SELECT * FROM users WHERE id = ?', [userId]);

  // 3. Store result in Redis with 1-hour expiration (TTL)
  await redis.setex(`user:${userId}`, 3600, JSON.stringify(user));
  return user;
}

4. CAP Theorem in Distributed Databases

The CAP Theorem states that a distributed data system can guarantee at most two of the following three properties simultaneously:

  • Consistency (C): Every read receives the most recent write or an error (e.g., PostgreSQL, Google Spanner).
  • Availability (A): Every non-failing node returns a valid response without guaranteeing the latest write (e.g., Apache Cassandra, DynamoDB).
  • Partition Tolerance (P): The system continues operating despite network message drops between distributed nodes. In real-world networks, network partitions are inevitable, so distributed systems must choose between CP (Consistency + Partition Tolerance) or AP (Availability + Partition Tolerance).

5. Database Scaling: Read Replicas & Sharding

Databases are typically the primary performance bottleneck in web applications. To scale beyond a single SQL instance:

  • Read Replicas (Primary-Replica Pattern): Route all state-changing writes (INSERT, UPDATE, DELETE) to a Primary database node, while read queries (SELECT) are distributed across multiple read-only replica nodes. Because most web apps have an 80:20 read-to-write ratio, read replication delivers 5x to 10x throughput instantly.
  • Database Sharding (Horizontal Partitioning): When a table grows to tens of millions of rows, split table rows across separate physical database instances based on a shard key (e.g., user_id % num_shards).

6. Asynchronous Processing & Message Queues (Kafka / RabbitMQ)

Synchronous request-response architectures fail under sudden traffic spikes. Instead of processing slow tasks (e.g., generating PDF invoices, sending confirmation emails, credit card fraud scoring) inside the HTTP request loop:

  1. The API server publishes a message to a queue (RabbitMQ, Apache Kafka, or AWS SQS) and immediately returns HTTP 202 Accepted to the user.
  2. A pool of background worker processes consumes messages asynchronously from the queue at a sustainable rate.
  3. If sudden traffic floods the system, the queue buffers the requests safely, preventing backend server crashes.
